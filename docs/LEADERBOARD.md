# Solo leaderboard verification

Online solo runs use a server-issued random seed and a server-validated skirmish map or campaign mission. For a skirmish, the start request includes `skirmishOpening` (`established` for Forward Base or `command-rig`) and `victoryMode` (`dominion` or `elimination`). In Elimination, relays still provide tactical effects, but victory requires removing the opposing combat force, powered defenses, and active production or command structures. For a campaign run, the server also checks that the same commander has a verified victory at that difficulty on the preceding route: First Harvest is always available, Black Shard opens both branch missions, and one completed branch opens Red Ledger. A verified archived Red Ledger or later victory preserves already-earned access for a pre-fork profile. A browser-only medal does not authorize a ranked ticket, though it still unlocks local practice. The request includes the selected doctrine, optional mission Field Order (`fieldOrderId`, default `none`), optional Carryover Intel (`carryoverId`, default `none`), and optional Route Requisition (`supplyId`, default `none`). On Red Ledger and Ashes in Transit, the server derives `routePayoffId` from the first verified Ghost Channel or Iron Current victory for that profile and difficulty; the start request cannot choose it. The server also derives `campaignVeteran` from the newest eligible version 30 or later verified victory on the preceding campaign route at the same difficulty. The client cannot submit a veteran manifest. The ticket locks the deployed unit type, original faction, Veteran or Elite rank, and optional Elite field modification; the replay spawns it beside the authored opening force. The server stores these choices in the run ticket and returns the locked setup. Replay verification reconstructs the selected opening and victory condition or campaign using that ticket, ignoring any choices claimed in the finish submission. The browser advances the simulation at a fixed 30 ticks per second and records each successful player command with its tick, arguments, and selected entity IDs. On a terminal result it sends this log and the final tick count. Loading a local save or leaving an unfinished match abandons its ranked run.

The server checks command types, arguments, order, selection and tick bounds, then replays the run in an isolated worker using the locked seed and scenario. It accepts a result only if its own simulation reaches victory or defeat at the submitted tick. The worker has a 30-second deadline and a 128 MB heap limit; no more than two verifications run concurrently, and the finish payload is capped at 1 MB. A run is verified once; an authenticated repeat finish for that same profile returns the stored verified result and original score without verifying or scoring again. Abandoned and superseded tickets remain rejected. Starting a new run invalidates a prior unfinished one. The server also rejects impossible simulated time relative to wall time and runs older than four hours.

Only replay-derived victories appear in the leaderboard with `verified: true`. Replay-derived kills are display information and do not change points. Current points are `max(0, round(5000 × difficultyMultiplier − simulationSeconds × 3))`, where the multiplier is 1 for easy, 1.5 for normal, and 2 for hard. Every verified terminal solo result also enters the authenticated commander's **My Battles** history, including defeats. `GET /api/records/history` requires that profile's bearer token and returns `{entries}` with the 30 newest results. Each entry includes its server-locked scenario and setup, replay-derived result, elapsed seconds and kills, and completion time. Campaign entries expose both `deployedVeteran` (the incoming attachment) and `campaignVeteran` (the survivor earned for the next sortie). Victories include the linked score while defeats have `score: null`; if an older linked score has been pruned, the history entry remains but its score is null. Other commanders cannot read these entries. The persistent history is capped at 10,000 results. Older stores with verified victory scores and no history backfill those victories once; older defeats were never stored and cannot be reconstructed. A duplicate finish does not add another entry. The public leaderboard remains victory-only. After an accepted solo result, the debrief queries that exact scenario, faction, difficulty, and setup for the top verified benchmark. If no matching victory exists or the board is unavailable, it says so instead of inventing a rival rank.

Completed live 1v1 matches have a separate **My 1v1 Matches** history. `GET /api/multiplayer/history` requires a bearer token and returns `{entries,total}` for that commander alone, newest first. `limit` defaults to 30 and accepts 1–100; `offset` defaults to 0 and accepts a nonnegative integer. Each entry identifies the opponent, map, victory mode, win or loss, match duration, finish reason, and completion time. Ranked entries also include rating before, after, and change. Both seat records are written before terminal notifications and survive a server restart; a match cannot add duplicate records. The persistent store retains at most 10,000 multiplayer seat records globally. These are authoritative server-recorded outcomes, separate from replay-verified solo scores.

**Ranked 1v1** uses a separate public queue, never pairing with Casual search or private rooms. It starts at a mutual ±100 rating-point window, widens by 100 every 10 seconds, and accepts any rating after 120 seconds; the closest eligible opponent is preferred. Casual search remains FIFO. The queued status reports the server-applied current-season rating and live window. The server fixes a random battlefield and Relay Dominion; both players mark ready and the host starts. Season 52 begins each commander at 1,200 rating because combat pursuit and Shard Valley change ranked matches. Season 51 introduced queued orders; Season 50 introduced Stormglass Bloom. A completed match transfers an integer Elo amount between the players with K=32; the server determines the winner from its authoritative simulation. A forfeit or final disconnect counts as a loss. A ranked result changes both commanders' season wins, losses, games, and rating once; Casual and private outcomes do not. The ranked season is independent of the solo replay rules version. `GET /api/multiplayer/rating` returns the authenticated commander's `{season,rating,wins,losses,games}`, and `GET /api/multiplayer/leaderboard` returns up to 100 rated commanders in `{entries}`. Commander Records shows the top ten and the signed-in commander's record. The server persists rating and active-match checkpoints across restart, including the ranked flag; an older running server lacking these endpoints leaves Ranked search locked in the client. Unlike the solo leaderboard, ranked multiplayer outcomes are server-recorded, not replay verified.

The client stores a failed finished-run submission as a ticket ID, profile ID, and local replay ID on this device, without copying the bearer token into that record. It retries after profile initialization, before another ranked ticket, or from Commander Records and the debrief. If a replay is missing, the profile differs, or the ticket has expired or been superseded, the interface explains why it cannot resubmit; the local replay remains available. This mechanism relies on browser storage for recovery. A failed archive write falls back to one direct finish request, which cannot be retried after a page loss.

`GET /api/leaderboard` accepts optional `difficulty` (`easy`, `normal`, or `hard`), `faction` (`aegis` or `vesper`), `mode` (`campaign` or `skirmish`), `scenarioId`, skirmish `skirmishOpening` (`established` or `command-rig`), `victoryMode` (`dominion` or `elimination`), and `aiCommanderProfileId` (`raider`, `relay-marshal`, or `siege-director`), campaign `doctrineId` (`standard`, `rapid`, `reinforced`, or `precision`), `fieldOrderId`, `carryoverId` (`none`, `assault`, or `signal`), `veteran` (`none`, `veteran`, or `elite`), `supplyId`, and `routePayoffId` (`none`, `ghost-channel`, or `iron-current`) query parameters. Route payoff filtering covers campaign Red Ledger and Ashes in Transit records; when a scenario is supplied with that filter, it must be one of those two missions. Filters combine when supplied together. A scenario ID must identify a known campaign mission or skirmish map; when `mode` is supplied, it must belong to that mode. Skirmish filters are invalid with campaign mode, and campaign-only filters are invalid with skirmish mode or a skirmish scenario. A Field Order ID must belong to the selected mission when `scenarioId` is supplied; `none` matches campaign runs without an order. Invalid filter values return HTTP 400. Skirmish score rows include the locked opening, victory condition, and server-derived enemy commander; older rows default to `established` and `dominion`. A `mode=skirmish` request without opening or victory-mode filters returns only Forward Base / Relay Dominion scores. If just one skirmish filter is supplied, the other defaults to Forward Base or Relay Dominion, including when `mode` is omitted. Campaign rows include doctrine, Field Order outcome, Carryover Intel, deployed Survivor Attachment, Route Requisition, and the Red Ledger or Ashes route payoff. The Survivor filter groups records by the incoming attachment rank; it is invalid for skirmish and the opening campaign mission. Current public results include verified version 57 for all three skirmish AI commanders and every campaign mission. This minimum version is a leaderboard comparability floor; older verified results remain in personal history. Rows sort by score descending with elapsed time and completion time as tie-breakers, and return at most 100 entries. The opponent-profile filter is valid only for skirmish. The debrief benchmark uses the exact server-derived profile. Separate filters keep unlike setups off the same ranked board.

`GET /api/campaign/progress` requires the commander's bearer token and returns difficulty-specific completed and unlocked missions, best medals, completed Field Orders, and the first verified branch route. It derives these from verified victories for that profile only. New medal rows store the server replay's star result; older verified wins without stored stars display a one-star completion. The campaign selector merges this record with browser-local practice progress and labels their sources, while ranked tickets continue to check the server record itself.

Carryover Intel is earned from a verified completed Field Order in the immediately preceding campaign mission, by the same profile at the same difficulty: the first order unlocks `assault`, the second `signal`. Verified Field Orders from version 4 through the current replay version count for progression unlocks; versions before 4 do not. Earlier achievements remain usable even when their scores are no longer ranked on the current board. `GET /api/campaign/carryover-unlocks?missionIndex=1&difficulty=normal` reports the authenticated profile's eligible IDs, verified `campaignVeteran` for that mission (or null), `rankedAvailable`, and the verified branch route for Red Ledger or Ashes. The briefing keeps local practice route choices when ranked access is unavailable. A run-ticket request rejects an unearned choice with HTTP 403. Local browser progress can still grant that choice for an unranked offline sortie. A winning replay chooses one living armed player unit deterministically by rank, kills, experience, then stable entity ID. A surviving rookie earns Veteran rank for the next sortie. The server stores only that validated terminal manifest, never a client-provided force list. The newest eligible verified victory supersedes older survivor records, including when no armed unit survived.

Solo verification proves the submitted actions produced the recorded result under the server's rules. It does not establish that a human played without automation, and a future game update should version the ruleset used by old replays. Unfiltered solo rankings combine different missions and maps, so cross-scenario point comparisons are not balanced. Multiplayer Ranked 1v1 uses authoritative live match outcomes and a separate season rating.
