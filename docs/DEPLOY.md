# Self-hosting

The container builds the Vite client and runs the Node HTTP/WebSocket server in one process. It serves the client, `/api`, and `/ws` from the same origin. Build and run it with Docker:

```sh
docker build -t frontier-command .
docker volume create frontier-data
docker run -d --name frontier-command \
  -p 3001:3001 \
  -v frontier-data:/data \
  frontier-command
curl http://localhost:3001/api/health
```

The default listener is `0.0.0.0:3001`. Set `PORT` and `HOST` to change it. The server writes its profile, friend, and score data to `/data/data.json` (`FRONTIER_DATA_FILE` can override that path). Keep `/data` on durable storage: replacing the container is safe when that volume is retained. Back up the volume regularly, and test restoring a backup before relying on it. Treat backups as private because they contain account tokens in hashed form and player records.

`/api/health` returns `rulesVersion` alongside `ok`. After replacing a release, check that it matches the browser build before expecting new solo runs to rank. If the versions differ, solo play continues as an explicitly unranked sortie until the server is updated.

## Public access

Put a reverse proxy with a valid HTTPS certificate in front of the container and expose only the proxy publicly. Forward ordinary HTTP requests to the container and support WebSocket upgrades for `/ws` (`Upgrade` and `Connection` headers); preserve the original `Host` and use a sufficiently long read timeout for live matches. The browser connects to `/ws` on the page's origin, so public play requires HTTPS at the proxy and `wss://` support there. The app does not configure TLS itself.

Run exactly one server instance against a data file at a time. Lobbies and live matches are held in memory, and the JSON file has no multi-writer coordination. Multiple replicas or concurrent containers can lose stored updates and cannot share live invitations or matches. Configure any proxy or platform routing to keep the service on that single instance. No external hosting provider or uptime is implied by this setup.

The server needs no deployment secret by default. Profile credentials are generated by the server and stored as hashes. Restrict access to the data volume and its backups; avoid publishing them or including them in container images.

## Local smoke test

After the `docker run` command above, check `docker ps` for a healthy status and visit `http://localhost:3001`. Create a profile, then check that data persists after recreating the container while retaining `frontier-data`:

```sh
docker rm -f frontier-command
docker run -d --name frontier-command -p 3001:3001 \
  -v frontier-data:/data frontier-command
curl -fsS http://localhost:3001/api/health
```

For a public smoke test, use the HTTPS URL configured at your reverse proxy, create a profile in two separate browsers, and verify friend requests and lobby invitations in both directions.
